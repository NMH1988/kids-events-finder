### T5.17 Malformed model output does not break the conversation (S) · status: todo · issue #49
**Serves:** Capstone (`docs/CAPSTONE_CHECKLIST.md`): multi-step reasoning, function calling, user interface and interaction quality; Legal (`docs/LEGAL_COMPLIANCE.md`): 2.10 (logs hold only event names), 4.3 (no unchecked model text shown or counted).
**Depends on:** T5.7
**Acceptance criteria** (drafted by Claude, approved by the owner on 2026-11-27)
- [ ] No model request holds a tool call without a result: when a model message holds a tool call that cannot be read (`invalid_tool_calls`), alone, next to a valid call that runs without a pause, next to a call that pauses for approval, or without an id, the model is told in the same turn, in fixed app text, that the call could not be read; the model's own raw arguments and error text are never copied into that note - verified by graph tests with a scripted model that check every request through `langchain-openai`'s message conversion and that every tool-call id has a result.
- [ ] A model that keeps sending invalid calls ends the turn at `config.AGENT_RECURSION_LIMIT` with the app's fixed error message, and nothing is stored half-way - verified by a graph test and an `AppTest`.
- [ ] Invalid calls never count as run: they are not in `tools_used`, get no source credit and are not in the feedback - verified by a runner test.
- [ ] The helper model's rewritten queries and rerank output pass `clean_text` (`src/safe_text.py`), so a lone surrogate there becomes U+FFFD and the search returns results instead of a tool error - verified by a retriever unit test with a stub helper model.
- [ ] An invalid call is logged only as an event name, never with model text - verified by a `caplog` test.
- [ ] The system prompt is unchanged - verified by the PR's diff (no change under `src/prompts/`).
**Notes:** found by the code and security reviews of T5.7 (round 1 of PR #48); both points were on `main` before T5.7 and outside its criteria, and the owner chose a ticket of their own on 2026-11-27. With today's graph an answer that holds only `invalid_tool_calls` goes to the grounding check and is stored, and `langchain-openai` sends it back as tool calls without results in the next turn; a message that holds a valid and an invalid call gets a result only for the valid one, so the next request of the same turn can fail (read in the code, not checked against the live API). The helper's rewrite and rerank output fail closed today (inside `_safe`, the search becomes a tool error).
