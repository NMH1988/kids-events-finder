### T5.17 Malformed model output does not break the conversation (M) · status: todo · issue #49
**Serves:** Capstone (`docs/CAPSTONE_CHECKLIST.md`): multi-step reasoning, function calling, user interface and interaction quality; Legal (`docs/LEGAL_COMPLIANCE.md`): 2.10 (logs hold only event names), 4.3 (no unchecked model text shown or counted), 6.3 (source credits only for calls that ran), register: processing (the feedback row: `tools_used`).
**Depends on:** T5.7
**Acceptance criteria** (drafted by Claude, approved by the owner on 2026-11-27; tightened after review round 1 of PR #50, approved by the owner the same day)
- [ ] No model request holds a tool call without a result: when a model message holds a tool call that cannot be read (`invalid_tool_calls`), alone, next to a valid call that runs without a pause, or next to a call that pauses for approval (approved, edited and rejected), the model is told in the same turn, in fixed app text, that the call could not be read; an invalid call without an id gets a fixed id from the app, so no request carries `"id": null`; the note is a ToolMessage placed right after the model's message (never a HumanMessage), so routing, `human_review`, `ToolNode` and the memory tool's checks still read the model's message as the step and the parent's message as the latest question; the model's own raw arguments and error text are never copied into the note - verified by graph tests with a scripted model that check every request through `langchain-openai`'s message conversion: every tool call has a non-null id and a result.
- [ ] A model that keeps sending invalid calls ends the turn at `config.AGENT_RECURSION_LIMIT` without an exception reaching the page (today's fixed error message; T5.4's step-limit message once that ticket is built), and the next question in the same conversation runs normally - verified by a graph test.
- [ ] Invalid calls never run and never count as run: the note is an `{"error": ...}` result, so it is never read as a calculation (the ticket comparison or budget box) or a memory save; an invalid call is never repaired from its raw arguments into a call that runs, never shown in the approval panel, not in `tools_used`, gets no source credit and is not in the feedback - verified by a runner test (an invalid `check_budget` and an invalid `remember_preference` fill no box and save nothing) and a graph test (an invalid outside call next to a valid one: the panel shows only the valid one, the tool runs only once).
- [ ] The helper model's rewritten queries pass `clean_text` (`src/safe_text.py`) before the embedding request, so a lone surrogate there becomes U+FFFD and the search returns results instead of a tool error (Pydantic accepts a lone surrogate in a parsed object, checked offline on 2026-11-27; the rerank output holds only ids, which are compared and never sent) - verified by a retriever unit test with a stub helper model whose queries hold a lone surrogate and an embedding stub that receives U+FFFD.
- [ ] An invalid call is logged only as an event name, never with model text - verified by a `caplog` test that checks the whole log record (`str(record.__dict__)`), not only its message.
- [ ] The system prompt is unchanged - verified by the PR's diff (no change under `src/prompts/`).
