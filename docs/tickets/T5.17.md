### T5.17 Malformed model output does not break the conversation (M) · status: todo · issue #49
**Serves:** Capstone (`docs/CAPSTONE_CHECKLIST.md`): multi-step reasoning, function calling, user interface and interaction quality; Legal (`docs/LEGAL_COMPLIANCE.md`): 2.10 (logs hold only event names), 2.11 (the memory tool's checks keep working next to an invalid call), 4.3 (no unchecked model text shown or counted), 6.3 (source credits only for calls that ran), register: processing (the feedback row: `tools_used`).
**Depends on:** T5.7
**Acceptance criteria** (drafted by Claude, approved by the owner on 2026-11-27; tightened after review rounds 1 and 2 of PR #50, approved by the owner the same day, and after round 3, approved on 2026-11-28)
- [ ] Every model request matches tool calls and results by position: the tool messages right after each assistant message answer exactly that message's tool calls, one each, and no tool message appears anywhere else. When a model message holds a tool call that cannot be read (`invalid_tool_calls`), alone, next to a valid call that runs without a pause, or next to a call that pauses for approval (approved, edited and rejected), the model is told in the same turn, in fixed app text, that the call could not be read; an invalid call without an id gets an id from the app that is unique in the whole conversation (built from the message's id and the call's position), so no request carries `"id": null` or a repeated id. A message that holds only invalid calls goes to a note step and back to the model, never to the grounding check, and `progress_labels` does not show the grounding label for it. The note is written together with the step's other results, after the step has run or been decided, never before: while the step is pending, the model's message stays the last message, so routing, `human_review`, `resume_turn` (the pending calls), `progress_labels` and the memory tool's checks (one save per topic in a step, saves only before other tool results) read it as today; the note is a ToolMessage with a fixed name from the app (never the model's tool name, which the memory tool's order check reads), never a HumanMessage; the model's own raw arguments and error text are never copied into it - verified by graph tests with a scripted model that run the position check on every request through `langchain-openai`'s message conversion, including after an edit (which rebuilds the model's message), with two invalid calls without ids in one step and with two steps that each hold one, and with a message that holds only invalid calls; and by tests where a valid memory save and an invalid call share a step (the save pauses, is saved when approved, and two saves for one topic are still refused) and where approve and edit run only the valid call.
- [ ] A model that keeps sending invalid calls stops at `config.AGENT_RECURSION_LIMIT` (`GraphRecursionError`, or T5.4's handling of it once that ticket is built), and the next question in the same conversation sends a request that passes the position check of criterion 1 - verified by a graph test.
- [ ] Invalid calls never run and never count as run: the note is an `{"error": ...}` result, so it is never read as a calculation (the ticket comparison or budget box) or a memory save; an invalid call is never repaired from its raw arguments into a call that runs, never shown in the approval panel, not in `tools_used`, gets no source credit and is not in the feedback - verified by a runner test (invalid `check_budget`, `compare_train_tickets` and `remember_preference` calls fill no box and save nothing) and a graph test (an invalid outside call next to a valid one: the panel shows only the valid one, the tool runs only once).
- [ ] An invalid call is logged only as an event name, never with model text - verified by a `caplog` test that checks the whole log record (`str(record.__dict__)`), not only its message.
- [ ] The system prompt is unchanged - verified by the PR's diff (no change under `src/prompts/`).
