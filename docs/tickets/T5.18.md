### T5.18 Every model step keeps its own message id (S) · status: todo · issue #51
**Serves:** Capstone (`docs/CAPSTONE_CHECKLIST.md`): multi-step reasoning, function calling; Legal (`docs/LEGAL_COMPLIANCE.md`): 4.3 (every stored tool result keeps the call it answers), 6.3 (no lost source credit for a step that ran).
**Depends on:** T5.7
**Acceptance criteria** (drafted by Claude, approved by the owner on 2026-11-28; tightened after review round 1 of PR #52, approved the same day)
- [ ] Every AI message the agent node stores has an id that no other message in the thread has: after `clean_ai_message`, the agent node checks the id against every message in the whole thread (`state["messages"]`, not the trimmed history the model sees), and when it is already used, the app gives the message a fresh random id of its own (a fixed prefix plus a UUID, never built from the repeated id, the thread, the question, the age groups or the trip settings), so a provider's id never replaces an earlier step; the new id stays in the checkpointer only (never logged, never in feedback records) - verified by graph tests with a scripted model: two steps with the same id, three steps with one id, an id repeated from an earlier turn that the trimmed history no longer shows, and a repeated id holding a lone surrogate (which `clean_id` turns into the same stored id); in each, every step is stored, every tool call keeps its result, the turn ends normally, `tools_used` counts every call and the earlier steps' source credits are still shown.
- [ ] Within one step, the grounding check and `human_review`'s edit branch still replace the message they mean to - verified by the existing tests passing and a test with a repeated id next to an edit and an answer that goes through the grounding check.
- [ ] The system prompt is unchanged - verified by the PR's diff (no change under `src/prompts/`).
**Notes:** found by security round 2 of PR #48 (T5.7), outside T5.7's criteria; the owner chose a ticket of its own on 2026-11-28. With the pinned `langchain-openai` 1.7.2 and no streaming, an AI message takes its id only from an `id` field inside the provider's message object (`_convert_dict_to_message`), which OpenAI's Chat Completions does not send; without it `langchain-core` gives each call a fresh `lc_run--<uuid>-<n>` id, so ids differ today (if the app ever streamed, the id would come from the stream pieces; re-check then). The risk is a provider behind OpenRouter that adds an `id` to the message and repeats it in two steps: `add_messages` would then replace the first step's message in place, so its tool result stays without the call it answers; the next request of that turn would carry a result with no call (which OpenAI's API normally refuses, not checked live), the grounding check would end the turn with an empty answer, and the step's source credit would be lost (read in the code, not seen or checked against the live API). T5.7 already keeps ids that differ only by a lone surrogate apart (`clean_id`). Message ids are not sent in Chat Completions requests, so the new id leaves the app nowhere; if the model call moves to the Responses API or starts sending ids, re-check the processing register. Tests use a scripted fake model only, no live provider call. Overlap with T5.17 (added after review round 1 of PR #52): T5.17 builds an app id for an invalid call from a hash of the message's id, so the message id must be made unique (this ticket) before any id is built from it; whichever ticket is built second adds a test with two steps that share a provider id and each hold an invalid call without an id, and keeps the other's tests. Review round 1 of PR #52 (code Needs changes, legal PASS with a note; owner decision of 2026-11-28): the cases above, the order after cleaning, the random id, the T5.17 overlap and the failure description.
