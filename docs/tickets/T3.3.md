### T3.3 Invite codes and rate limits (M) · status: todo · issue #5
**Serves:** Capstone: none (deployment); Legal: 2.1, 2.3, 2.7, 2.9, processing register (invite codes), "Before a public deployment" (app features).
**Depends on:** none
**Acceptance criteria** (drafted by Claude, approved by the owner on 2026-11-23)
- [ ] Invite codes are stored only as hashes with counters; no code in plain text is stored or logged - verified by unit tests on the store.
- [ ] A per-code daily limit (in `src/config.py`) is checked per code and per session before any model call; over the limit the parent sees a fixed message and no model call is made - verified by unit tests with a mocked model.
- [ ] Without a valid code the chat makes no model call - verified by an AppTest.
- [ ] The processing register row (legitimate interest, Art. 6(1)(f)) covers the invite codes and request counts with their retention (2.7) - verified by `legal-reviewer` PASS.
- [ ] `security-reviewer` without Medium or higher (spend protection) - verified by its report on the PR.
**Notes:** issue #5 also asks for a per-IP limit. Streamlit does not hand the app the client IP; that depends on the hosting (a reverse proxy header) or on T4.1's back end, so it is not a criterion here. If the owner keeps it, it needs: a keyed or salted hash, no plain IP in logs, a short retention (e.g. end of day), and the register row and 2.7 updated (a hashed IP is still personal data). Owner decides: per-IP limit, or per code and session only.
